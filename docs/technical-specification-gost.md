# Техническое задание (проект, формат близкий к ГОСТ 34)

## 1. Общие сведения

### 1.1 Наименование системы
Единая цифровая платформа управления деятельностью подразделения (далее — Система).

### 1.2 Основание для разработки
Необходимость замены разрозненных Google-таблиц и скриптов централизованным производственным решением с юридически значимым учётом.

### 1.3 Заказчики и пользователи
- Диспетчер;
- Начальник караула;
- Администратор;
- Руководство;
- Внешние интеграционные потребители (Telegram-бот, API-клиенты).

## 2. Назначение и цели создания системы

### 2.1 Назначение
Автоматизация процессов учёта выездов, личного состава, техники, ГСМ, документооборота, аналитики и формирования отчётности.

### 2.2 Цели
- Централизация хранения данных;
- Снижение ручного труда и ошибок;
- Обеспечение прозрачного контроля ресурсов;
- Поддержка аналитики и KPI;
- Обеспечение real-time мониторинга в web и TV-режиме.

## 3. Характеристика объекта автоматизации
Объектом автоматизации являются процессы диспетчеризации и оперативного управления подразделением: вызовы, выезды, сменность, ресурсы, техника, документы и отчётность.

## 4. Требования к системе

### 4.1 Функциональные требования

#### 4.1.1 Модуль «Выезды»
- Регистрация вызова и выезда;
- Учёт временных отметок (вызов/выезд/прибытие/возвращение);
- Привязка техники и караула;
- Автоматический расчёт длительности;
- Экспорт сводок в PDF/Word.

#### 4.1.2 Модуль «Личный состав»
- Карточка сотрудника;
- Звание, должность, допуски;
- История участия в выездах;
- Учёт часов и нагрузки.

#### 4.1.3 Модуль «Караулы и сменность»
- Формирование караулов;
- Графики смен;
- Замещения;
- Контроль переработок.

#### 4.1.4 Модуль «Техника»
- Карточка ТС;
- Пробег, состояние, ТО;
- История выездов;
- Расчёт моточасов.

#### 4.1.5 Модуль «ГСМ»
- Учёт заправок;
- Остатки и норматив;
- Автоматическое списание;
- Пороговые предупреждения (75% / 50%).

#### 4.1.6 Модуль «Оборудование»
- Инвентаризация;
- Закрепление за техникой;
- Учёт отказов и актов.

#### 4.1.7 Модуль «Документооборот»
- Приказы, путевые листы, акты;
- Автонумерация;
- Хранение сканов;
- Опционально ЭП.

#### 4.1.8 Модуль «Аналитика и дашборд»
- Динамика выездов;
- KPI;
- Время реагирования;
- Ложные вызовы;
- Прогнозирование.

#### 4.1.9 TV Panel
- Полноэкранное отображение статусов;
- Active dispatches;
- Статусы техники и ГСМ;
- Обновление через WebSocket.

#### 4.1.10 Telegram-бот
- Публикация сводок;
- Уведомления о выездах;
- Уведомления о низком уровне ГСМ;
- Отчёты по команде.

### 4.2 Нефункциональные требования
- До 100 одновременных пользователей;
- Время ответа API < 300 мс (P95 при номинальной нагрузке);
- Обновление real-time < 1 сек;
- JWT + RBAC;
- Audit trail;
- TLS/HTTPS;
- Резервное копирование и контроль восстановления.

### 4.3 Требования к надёжности
- Регулярные backup политики;
- Мониторинг состояния БД и сервисов;
- Журналирование транзакций;
- Защита от потери данных.

### 4.4 Требования к интерфейсу
- Минималистичный UX;
- Быстрый ввод;
- Клавиатурные шорткаты;
- Цветовая индикация;
- Тёмная тема для диспетчерской.

### 4.5 Требования к безопасности
- Ролевой доступ;
- Разделение прав чтения/изменения/администрирования;
- Аудит критичных операций;
- Политики хранения и удаления персональных данных.

## 5. Состав и содержание работ

1. Проектирование: требования, ERD, API контракты.
2. Backend: модели, CRUD, auth, аудит, тестирование.
3. Frontend: диспетчерская, формы, аналитика, TV panel.
4. Интеграции: Telegram, отчётность.
5. Аналитика: KPI, агрегаты, визуализация.
6. Тестирование: функциональное, нагрузочное, безопасность, UX.
7. Ввод в эксплуатацию: Docker/Nginx/PM2/backup.

## 6. Порядок контроля и приёмки
- Приёмка по этапам с демонстрацией функциональных сценариев;
- Проверка SLA по response-time и real-time обновлению;
- Подписание итогового акта после прохождения пилотной эксплуатации.

## 7. Требования к документированию
- Архитектурная документация;
- Регламент администрирования и резервного копирования;
- Пользовательские инструкции по ролям;
- API-спецификация (OpenAPI).

## 8. Источники разработки
- Описание текущих бизнес-процессов подразделения;
- Текущие Google-таблицы и форматы отчётности;
- Нормативные требования по учёту и хранению данных.
